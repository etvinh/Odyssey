# API Spec — Restaurant Ops Backend

Design intent: a small, boring REST surface where every read maps to exactly one screen region and every write maps to exactly one interactive flow from the component inventory. All shapes originate in Drizzle → drizzle-zod → `@hono/zod-openapi` → Orval, so the types below describe the contract, not hand-written DTOs. Hook names are what Orval generates from the `operationId`. Generated output lands in `packages/api-client` (committed, regenerated by `pnpm gen:contract`); the domain types and enums both sides import live in `packages/types`.

Base path: `/api/v1`. All money in **integer cents** (formatting to `$12.50` is `formatMoney` in `packages/shared`). All timestamps ISO 8601 UTC.

---

## 0. Cross-cutting contracts

**Error shape (every non-2xx):**
```ts
{ error: { code: string; message: string; fields?: Record<string, string> } }
```
`code` is a stable machine string (`VALIDATION_FAILED`, `NOT_FOUND`, `ITEM_UNAVAILABLE`, `INVALID_TRANSITION`, `CATEGORY_NOT_EMPTY`). `fields` powers per-input error text in `FormRow`; `message` powers `Toast` (error) and `ErrorState`.

**List envelope (every collection read):**
```ts
type ListMeta = { total: number; page: number; pageSize: number };
type ListEnvelope<T, M = {}> = { data: T[]; meta: ListMeta & M };
```
Every collection read returns this shape, including the unpaginated menu reads — there `total` equals `data.length` and `page`/`pageSize` describe the single page. Endpoints needing more **widen** `meta` through `M` rather than replacing it, so `DataTable`'s pagination footer ("24 of 128 orders") types against `ListMeta` alone and works on every table.

**Enums — single source.** `orderStatus`, `orderChannel`, `dayOfWeek` are Drizzle `pgEnum`s, surfaced through drizzle-zod into OpenAPI and re-exported from `packages/types`. `StatusBadge` and `SegmentedControl` consume that type; no frontend copy exists.

```ts
orderStatus  = 'pending' | 'confirmed' | 'preparing' | 'ready' | 'completed' | 'cancelled'
orderChannel = 'dine_in' | 'takeaway' | 'delivery'
```

## 1. Summary — Home

### `GET /summary` · `useGetSummary`
**For:** everything above the fold on Home in one round trip — avoids four spinners racing each other.
**Returns:**
```ts
{
  today:     { orderCount: number; revenueCents: number };   // revenue = completed orders only
  yesterday: { orderCount: number; revenueCents: number };   // deltas are today.x - yesterday.x
  popularItems: Array<{
    menuItemId: string;
    name: string;
    orderCount: number;      // orders in the window that contained this item
    shareOfOrders: number;   // orderCount / total orders in the window
  }>;                        // top 5, last 7 days
}
```
There is deliberately **no `pendingCount` here.** Home's third KPI reads `meta.statusCounts.pending` from `GET /orders`, which that page already fetches for the needs-attention table. One number, one source, one invalidation — a count served by two endpoints is a count that can disagree with itself mid-render.

**Maps to:** `HomeKpiRow` (three `KpiStat`s + delta context lines; pending comes from the orders query), `PopularItemsList` (name + `ProgressBar` from `shareOfOrders`). Skeleton: KPI-card `Skeleton` variant.

`NeedsAttentionTable` does **not** get its own endpoint — it calls `GET /orders?status=pending&pageSize=5`. Same data, same hook, same cache as the Orders page, and confirming an order from Home invalidates one query key instead of two.

## 2. Orders

### `GET /orders` · `useListOrders`
**Query:** `status?` (enum), `search?` (order number or customer name), `page?`, `pageSize?`, `sort?` (`placedAt.desc` default)
**For:** the Orders page list and the Home needs-attention slice.
**Returns:** list envelope of:
```ts
{
  id: string; orderNumber: string;            // "1042" — display id, mono
  customer: { id: string; name: string } | null;  // null = walk-in
  channel: orderChannel;
  status: orderStatus;
  itemCount: number;
  totalCents: number;
  placedAt: string;
  allowedActions: OrderAction[];   // same server-computed field as the detail read
}
```
`allowedActions` is on the **row**, not just the detail response. Without it any list-level action button would have to re-derive the state machine on the client, which is the one thing this contract exists to prevent. It is computed from `status` in the same query and costs a handful of bytes per row.

`meta` widens the envelope with `statusCounts: Record<orderStatus, number>` — computed in the same query so `OrdersFilterBar`'s segmented control shows live counts ("Pending 4") without a second request. `statusCounts` honours `search` but **ignores the `status` filter**, so the counts stay whole while a filter is applied — and so Home's pending KPI is correct even though its request is `?status=pending`.
**Maps to:** `OrdersTable` (row shape is exactly one row), `OrdersFilterBar` (counts), `SearchField`, table `EmptyState` ("No orders match these filters") vs `ErrorState` (retry refetches this hook).

### `GET /orders/{id}` · `useGetOrder`
**For:** the drawer. Everything the detail view needs, nothing the list already had to know.
**Returns:**
```ts
{
  id: string; orderNumber: string;
  customer: { id: string; name: string; phone: string | null } | null;
  channel: orderChannel; status: orderStatus;
  items: Array<{ id: string; menuItemId: string; name: string; unitPriceCents: number; quantity: number; lineTotalCents: number }>;
  // name & unitPrice are snapshotted onto order_items at creation — renaming a menu item later must not rewrite history
  totalCents: number;
  kitchenNote: string | null;
  timeline: Array<{ status: orderStatus; changedAt: string }>;  // from order_events, powers the drawer timeline
  allowedActions: OrderAction[];                          // see below — server tells the UI which buttons exist
}
```
**Maps to:** `OrderDetailDrawer` — items list, mono totals, kitchen note, timeline, and the action buttons rendered **only** from `allowedActions` (the frontend never re-implements the state machine).

### `POST /orders` · `useCreateOrder`
**Body:**
```ts
{ customer?: { id: string }                                                    // existing customer
            | { name: string; phone?: string; email?: string; preferences?: string[] };  // new — created in the same transaction
  channel: orderChannel; kitchenNote?: string;
  items: Array<{ menuItemId: string; quantity: number }> }   // no prices in the payload — ever
```
**Behavior:** validates non-empty items and quantity ≥ 1 (`422 VALIDATION_FAILED` with `fields`), rejects any unavailable or deleted menu item (`409 ITEM_UNAVAILABLE`, message names the item), snapshots current names/prices, computes totals server-side, creates the order as `pending` (or `confirmed` when settings `isAutoAccepting` is on — deliberate backend behavior worth one line in the README), writes the first `order_events` row.

`customer` is a **discriminated union, not two optional fields** — `{ id }` attaches an existing customer, an object with a `name` creates one, and omitting the key entirely is a walk-in. It generates as an OpenAPI `oneOf`, so Orval emits a real union type and the frontend cannot construct a body with both. There is no separate `POST /customers`: a new customer is inserted **inside the same transaction as the order**, so a rejected order can never leave behind a customer with no orders. Field errors key as `customer.name`.
**Returns:** `201` with the full `GET /orders/{id}` shape.
**Maps to:** `OrderCreateModal` — customer `Select`, channel `SegmentedControl`, item picker + `Stepper` cart (cart total shown client-side is a *preview*; the authoritative total comes back in the response), kitchen-note `TextArea`, field errors into `FormRow`, success `Toast` "Order #1043 created". Invalidates `listOrders`, `getSummary`, and `listCustomers` (a new customer may have been created).

### `POST /orders/{id}/actions` · `useApplyOrderAction`
**Body:** `{ action: OrderAction }` where
```ts
OrderAction = 'confirm' | 'start_preparing' | 'mark_ready' | 'complete' | 'cancel'
```
**For:** the whole point of "not a loose client-controlled field." Status is never PATCHed; the client requests a named action and the server owns the machine:

| From \ Action | confirm | start_preparing | mark_ready | complete | cancel |
|---|---|---|---|---|---|
| pending | → confirmed | — | — | — | → cancelled |
| confirmed | — | → preparing | — | — | → cancelled |
| preparing | — | — | → ready | — | → cancelled |
| ready | — | — | — | → completed | → cancelled |
| completed / cancelled | terminal — every action → `409 INVALID_TRANSITION` |

`cancel` is legal from `ready`: a plated order still gets cancelled when the customer leaves, and forbidding it would be a modelling artifact rather than a rule the restaurant actually has. Only `completed` and `cancelled` are terminal.

**Returns:** `200` with the full order detail shape (fresh `status`, appended `timeline` entry, recomputed `allowedActions`).
**Maps to:** action buttons in `OrderDetailDrawer` and the inline next-action `Button` in `NeedsAttentionTable`, both rendered from the server's `allowedActions` — the drawer from the detail read, the row from its own `allowedActions` field. Cancel routes through `ConfirmDialog`. Success `Toast` echoes the verb ("Order #1042 marked ready"). Invalidates `listOrders`, `getOrder(id)`, `getSummary`.

## 3. Menu

### `GET /menu/categories` · `useListMenuCategories`
**Returns:** list envelope (unpaginated) of `{ id: string; name: string; sortOrder: number; itemCount: number }`
**Maps to:** `MenuCategorySection` headers / category tabs (`SegmentedControl`), the category `Select` inside `MenuItemModal`.

### `POST /menu/categories` · `useCreateMenuCategory` — body `{ name }`, returns `201` category.
### `PATCH /menu/categories/{id}` · `useUpdateMenuCategory` — body `{ name?, sortOrder? }`.
### `DELETE /menu/categories/{id}` · `useDeleteMenuCategory` — `409 CATEGORY_NOT_EMPTY` if it still has items; `204` otherwise. Routes through `ConfirmDialog`.

### `GET /menu/items` · `useListMenuItems`
**Query:** `categoryId?`, `available?`, `search?`
**Returns:** list envelope (unpaginated) of `{ id: string; categoryId: string; name: string; description: string | null; priceCents: number; isAvailable: boolean }`
**For:** the Menu page and the item picker inside `OrderCreateModal` (picker calls it with `available=true` — the backend still re-checks at create time; the filter is UX, the 409 is the guarantee).
**Maps to:** `MenuCategorySection` item rows (name, mono price, `StatusBadge` availability), per-category `EmptyState`.

### `POST /menu/items` · `useCreateMenuItem`
**Body:** `{ categoryId; name; description?; priceCents; isAvailable }` — `422` with `fields` on missing name, negative price, unknown category.
**Maps to:** `MenuItemModal` create mode.

### `PATCH /menu/items/{id}` · `useUpdateMenuItem`
**Body:** any subset of the create body. The availability `Switch` on the row calls this with just `{ isAvailable }` — optimistic toggle, rollback + error `Toast` on failure.
**Maps to:** `MenuItemModal` edit mode, row `Switch`.

### `DELETE /menu/items/{id}` · `useDeleteMenuItem`
Soft-delete (`deletedAt`) so historical order items keep a valid FK; deleted items vanish from all list reads. `204`. **Maps to:** delete flow in `MenuItemModal` → `ConfirmDialog`.

## 4. Customers — CRM

### `GET /customers` · `useListCustomers`
**Query:** `search?`, `sort?` (`totalSpendCents.desc` default), `page?`, `pageSize?`
**Returns:** list envelope of:
```ts
{ id: string; name: string; phone: string | null; email: string | null;
  orderCount: number; totalSpendCents: number; lastOrderAt: string | null }
```
Derived totals are computed in SQL (lateral join / grouped subquery), not N+1 and not stored values that drift.
**Maps to:** `CustomersTable` (`Avatar` initials, mono spend column), `SearchField`, `EmptyState`.

### `GET /customers/{id}` · `useGetCustomer`
**Returns:** the row shape above plus `preferences: string[]` and `recentOrders` (last 10).

`recentOrders` reuses the **`GET /orders` row type exactly** — same schema, same fields, same `allowedActions`. A bespoke subset here would be a third order shape in the contract for rows that are already clickable into a real order, and would need its own renderer.

`preferences` is free text the restaurant keeps about a customer. It is **read-only** in this build: there is no `PATCH /customers/{id}`, so the drawer must present preferences as display, not as an editable field.
**Maps to:** `CustomerDetailDrawer` — stat trio (orders / spend / last visit), preferences as neutral `StatusBadge`s, order history list; tapping a history row opens `OrderDetailDrawer` via the already-cached `useGetOrder`.

Customers have **no create endpoint of their own.** A new customer is created only as part of `POST /orders`, which is the only flow that produces one — see the `customer` union there. `OrderCreateModal`'s `Select` still offers "+ New customer" inline; it just submits within the order rather than ahead of it.

## 5. Settings

### `GET /settings` · `useGetSettings`
**Returns:** the singleton settings row:
```ts
{
  isAcceptingOrders: boolean;
  isAutoAccepting: boolean;
  prepTimeMinutes: number;        // 5–120, range enforced server-side too
  openingHours: Array<{ day: dayOfWeek; opensAt: string | null; closesAt: string | null }>; // null pair = closed
}
```
**Maps to:** `ServiceSettingsCard` (`Switch` ×2, `Stepper`), `OpeningHoursCard` (`FormRow` per day), and `ServiceStatusPill` in the `AppShell` header — the pill derives open/closed from `isAcceptingOrders` + current time against `openingHours`, in a shared `packages/shared` util so backend tests and the pill agree. **No timezone is modelled** — comparison is server-local. Out of scope, and stated in the tradeoffs note.

### `PATCH /settings` · `useUpdateSettings`
**Body:** any subset of the shape above. Validates `prepTimeMinutes` range and that `opensAt < closesAt` per day (`422` with `fields` keyed like `openingHours.2.closesAt`). That rule makes a cross-midnight close (18:00–01:00) unrepresentable, as does the single interval per day for split lunch/dinner service — both are accepted scope cuts, not oversights.
**Maps to:** both settings cards' `SaveBar`s — each card PATCHes only its own fields, so the two cards stay independently dirty/clean. Success `Toast` "Service settings saved". Invalidates `getSettings` (and the pill re-derives).

## 6. Wiring summary

| Endpoint | Hook | Consumed by |
|---|---|---|
| GET /summary | useGetSummary | HomeKpiRow, PopularItemsList |
| GET /orders | useListOrders | OrdersTable, OrdersFilterBar, NeedsAttentionTable |
| GET /orders/{id} | useGetOrder | OrderDetailDrawer |
| POST /orders | useCreateOrder | OrderCreateModal (including inline "+ New customer") |
| POST /orders/{id}/actions | useApplyOrderAction | OrderDetailDrawer actions, NeedsAttentionTable inline button |
| GET /menu/categories | useListMenuCategories | MenuCategorySection, MenuItemModal Select |
| POST /menu/categories | useCreateMenuCategory | Menu page category management |
| PATCH /menu/categories/{id} | useUpdateMenuCategory | Menu page category management |
| DELETE /menu/categories/{id} | useDeleteMenuCategory | Menu page category management → ConfirmDialog |
| GET /menu/items | useListMenuItems | MenuCategorySection rows, OrderCreateModal picker |
| POST /menu/items | useCreateMenuItem | MenuItemModal (create) |
| PATCH /menu/items/{id} | useUpdateMenuItem | MenuItemModal (edit), availability Switch |
| DELETE /menu/items/{id} | useDeleteMenuItem | MenuItemModal delete → ConfirmDialog |
| GET /customers | useListCustomers | CustomersTable |
| GET /customers/{id} | useGetCustomer | CustomerDetailDrawer |
| GET /settings | useGetSettings | ServiceSettingsCard, OpeningHoursCard, ServiceStatusPill |
| PATCH /settings | useUpdateSettings | Both SaveBars |

**Hook naming.** Every hook is `use{Verb}{Resource}` — `Get` for a single read, `List` for a collection, `Create`/`Update`/`Delete` for the obvious mutations, `Apply` for the action endpoint. Orval derives these from `operationId`, so the convention is enforced at the OpenAPI layer: an `operationId` that would generate a name off this pattern is the defect, not the hook.

**Invalidation map (React Query):** createOrder → `orders`, `summary`, `customers` · applyOrderAction → `orders`, `order(id)`, `summary`, `customer(id)` if attached · menu mutations → `menuItems`, `menuCategories` · updateSettings → `settings`.

**Where the tests aim:** the transition table (every legal move + a handful of illegal ones asserting `409 INVALID_TRANSITION`), createOrder total computation + `ITEM_UNAVAILABLE`, settings validation. That covers the brief's "targeted backend tests for key order flows" exactly.
