## Platform

web

The dashboard is an Expo + React Native app rendered to web via React Native Web. Web is the only verified target; native is not exercised or claimed. The RN substrate is a stack requirement of the brief, not a native-delivery commitment.

## Stack

Fixed by the brief. Not open for substitution — Next.js, NestJS, Prisma, tRPC, Supabase, Firebase, and handwritten frontend API types are explicitly excluded.

- **Monorepo:** pnpm workspace + Turborepo.
- **`apps/dashboard`:** Expo + React Native + React Native Web. Expo Router for file-based routing.
- **`services/backend`:** Hono on Cloudflare Workers, `@hono/zod-openapi`.
- **Data:** PostgreSQL (local Docker) + Drizzle ORM + drizzle-zod.
- **Contract flow:** Drizzle schema → drizzle-zod → Hono/OpenAPI → Orval → generated hooks. No hand-written DTOs, no duplicated enums.
- **Client state:** TanStack Query via Orval-generated hooks.

**Packages**

| Package | Holds |
|---|---|
| `packages/ui` | Design tokens and RN primitives. The design system. |
| `packages/types` | drizzle-zod-derived domain types and enums (`orderStatus`, `orderChannel`, `OrderAction`, `dayOfWeek`), imported by both the Worker and the dashboard. |
| `packages/api-client` | Orval output. Committed to the repo, regenerated by `gen:contract`. |
| `packages/shared` | Cross-cutting utilities: `formatMoney`, the open/closed service-status derivation. |

**Database connectivity.** Cloudflare Workers cannot open a raw TCP Postgres connection through the usual Node driver path, so the Worker reaches Postgres via `postgres.js` through `drizzle-orm/postgres-js` over `cloudflare:sockets` with `nodejs_compat`. Migrations (drizzle-kit) and the seed script run as plain Node processes against the same `DATABASE_URL`. Two connection paths, one database — see `../docs/adr/0001-workers-postgres-connectivity.md`.

**Local only.** No deployment target. The deliverable is a repository that runs locally via Docker Compose plus `pnpm dev:backend` and `pnpm dev:dashboard`.

## Users

**Primary:** the owner/manager of a small independent restaurant, working the back office rather than the floor. They use Odyssey between services and in quiet moments during one — reviewing how the day is going, advancing orders that are stuck, editing the menu, looking up a customer, adjusting service settings.

Situation: desktop or laptop, seated, with time to read a table. Sessions are short and repeated rather than continuous. The user is one person wearing every hat, so the app is checked in gaps, not monitored.

Consequence for design: Home, CRM, and Settings carry real weight rather than being satellites of Orders. Information density is affordable; the interface assumes a pointer, a keyboard, and a wide viewport as the primary case, with one breakpoint below which the sidebar collapses.

Not confirmed: whether floor staff on a tablet ever share the same install. Not designed for a live-rush touch terminal, and mid-service floor use is not a supported scenario.

## Product Purpose

Odyssey is a restaurant operations app: one place for a small restaurant's orders, menu, customers, and service settings.

- **Home** — the state of the day: order count, revenue, pending orders, popular items, and the orders needing attention.
- **Orders** — list, filter, and search; detail view with items, totals, kitchen note, and timeline; advance status through server-validated actions.
- **Menu** — categories and items, prices, availability toggles, soft deletes that preserve order history.
- **CRM** — customer list with order count, total spend, and last visit; detail view with preferences and recent order history.
- **Settings** — accepting orders, auto-accept, prep time, opening hours; the header service pill derives from these.

Success is the manager knowing the state of the day in one glance at Home, and every routine change being one obvious flow away.

## Positioning

Odyssey is built to a take-home assignment: a small but complete fullstack restaurant operations product, on a fixed stack, within a 1–2 day timebox.

That framing sets the priorities:

- **Depth over breadth.** The five required pages plus a UI library route, finished, rather than more surfaces done thinly.
- **Discipline is the demonstrated quality.** One type source, one state machine owned by the server, one design token file, every read mapping to exactly one screen region.
- **Scope is stated, not hidden.** Everything deliberately omitted is written down (see Capabilities and Constraints, and the tradeoffs note in the README) rather than left for a reader to discover.

No market claims, competitor comparisons, customer counts, or pricing may be invented. There are none.

## Operating Context

- **Order lifecycle:** `pending → confirmed → preparing → ready → completed`. `cancel` is legal from `pending`, `confirmed`, `preparing`, and `ready`. `completed` and `cancelled` are terminal. The client never sets status directly; it requests a named action and the server decides. The UI renders action buttons only from the server's `allowedActions`, which is present on both list rows and detail responses.
- **Order channels:** `dine_in`, `takeaway`, `delivery`.
- **Money:** integer cents everywhere in the contract. Formatting to `$12.50` is `formatMoney` in `packages/shared`. Numeric columns are right-aligned and monospaced.
- **History integrity:** order items snapshot item name and unit price at creation, so later menu edits never rewrite past orders. Menu items are soft-deleted for the same reason.
- **Walk-ins:** an order's customer may be `null`. Attaching a customer is optional, and a new customer can be created inline from the order flow rather than dead-ending it. There is no standalone customer-create endpoint — `POST /orders` takes a `customer` union and inserts the new customer in the same transaction, so a rejected order cannot strand a customer with no orders.
- **Service status:** open/closed is derived from `isAcceptingOrders` plus the current time against `openingHours`, in a shared util so the backend and the header pill cannot disagree.
- **Repo conventions:** issues and specs live as local markdown under `.scratch/<feature-slug>/`; the domain glossary is `../CONTEXT.md` at the root with ADRs under `../docs/adr/`. Five canonical triage labels. See `../CLAUDE.md`.

## Capabilities and Constraints

### Confirmed constraints

- **The stack is fixed** by the brief and its exclusion list.
- **The design system is hand-built** on React Native primitives (`View`, `Text`, `Pressable`) with `StyleSheet.create` over a typed token module in `packages/ui`. No third-party component library. MUI was considered and rejected — it targets `react-dom` and has no React Native runtime; see `../docs/adr/0002-react-native-primitives.md`.
- **Tokens are centralized** in one module and named semantically (`surface`, `foreground`, `border`, `danger`) rather than by value, so a second theme is a swap rather than a rewrite.
- **The generated API client is committed** to the repository. `typecheck` depends on `gen:contract`, so a stale client fails locally.

### Error contract

Every non-2xx returns `{ error: { code, message, fields? } }`. Stable codes: `VALIDATION_FAILED`, `NOT_FOUND`, `ITEM_UNAVAILABLE`, `INVALID_TRANSITION`, `CATEGORY_NOT_EMPTY`. `fields` drives per-input errors in `FormRow`; `message` drives error `Toast` and `ErrorState`. Client-side validation uses the same drizzle-zod-derived schemas the server validates against, via React Hook Form's `zodResolver`; the server response remains authoritative for anything the client cannot know (item availability, cross-field opening-hours rules).

### Deliberate backend behaviors

`isAutoAccepting` creates orders as `confirmed` rather than `pending` — seeded off, so Home's pending KPI and needs-attention slice are populated by default. `GET /orders` returns `meta.statusCounts` so filter chips show live counts without a second request. The Home needs-attention slice reuses the orders query rather than owning an endpoint.

### Deliberately out of scope

Each of these is a scope decision, not an oversight, and each is named in the README's tradeoffs note:

- **Timezone handling.** No restaurant timezone; times are server-local. This makes `summary.today` and the service pill approximate for any restaurant not in the server's zone.
- **Cross-midnight closing.** `opensAt < closesAt` is enforced, so an 18:00–01:00 service cannot be represented.
- **Split service.** One opening interval per day; lunch-and-dinner hours cannot be represented.
- **Order editing after creation.** No `PATCH /orders`. Orders are immutable once placed.
- **Customer editing.** No `PATCH /customers/{id}`. A customer can be created and read but never corrected; preferences are set at creation only and render as display. The brief asks to *view* customers in CRM, so this is a scope decision.
- **Reopening a completed order.** `completed` is terminal with no undo.
- **Authentication, staff accounts, and roles.** Single implicit operator.
- **Realtime updates.** Request/response with React Query invalidation; no websockets or polling.
- **Multi-location.** Single restaurant.
- **Currency abstraction.** USD assumed; no currency field.
- **Dark theme.** Light only, with semantic tokens structured so dark is a later swap.
- **Native verification.** Built on RN primitives but exercised only on web.

## Product Principles

1. **The server owns the truth; the UI renders it.** Status transitions, totals, availability, and permitted actions come from the server. The frontend never re-implements the state machine or computes an authoritative price.
2. **One source per type.** Enums, shapes, and validation flow from the database schema outward through `packages/types` and `packages/api-client`. A hand-copied enum or a hand-written DTO is a defect, not a shortcut.
3. **Every read serves one region; every write serves one flow.** Endpoints are shaped by the screens that consume them, which is why Home is one round trip and the needs-attention slice reuses the orders query.
4. **History is immutable.** Snapshots and soft deletes over cascading edits. Changing today's menu must never change last week's receipts.
5. **Finish over expand.** Depth and consistency in what exists, not the count of surfaces. Everything cut is written down.

## Accessibility & Inclusion

**Target: WCAG 2.1 AA.** Implemented in the parts that are cheap and structural; not audited, and the gap is stated in the tradeoffs note rather than implied to be closed.

What is actually implemented:

- Visible, unambiguous focus indication on every interactive element, and keyboard-complete flows on web including drawers, dialogs, segmented filters, and availability switches.
- `accessibilityRole` on tables, rows, cells, dialogs, and drawers, so React Native Web emits real ARIA semantics rather than anonymous `div`s.
- Labels bound to inputs through `FormRow`; `Toast` and `InlineAlert` announced to assistive technology.
- Status never carried by color alone — `StatusBadge` reads by text, and progress bars carry their number.
- Contrast checked against AA for text and UI boundaries in the token palette.

Not done: a full audit, screen-reader testing, or any native-platform accessibility work.
